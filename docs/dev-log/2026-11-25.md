- `docker-compose.yml`, 이미지 `postgres:16`, 포트 5432

`auth / user / question / answer / note / card / notification / ai / common`
(`auth`는 아직 비어 있어 `.gitkeep`만 있음)

## 3. 결정 사항과 이유

### 3-1. Spring AI 2.1.0 사용 (요청은 1.0.0)
- **선택**: Maven Central에서 Boot 4.x에 맞는 버전을 조회해 2.1.0(최신 정식판)으로 결정
- **이유**: Spring AI 1.0.0은 Boot 3.4/3.5 기준이라 Boot 4.2.0과 호환되지 않을 가능성이 컸다. 1.0.0을 그대로 쓰면 기동 시점에 깨질 위험이 있어, 먼저 호환 버전을 찾기로 했다.
- **스타터 이름도 변경**: `spring-ai-openai-spring-boot-starter`는 1.0.0 정식판에서 `spring-ai-starter-model-openai`로 바뀜
- **검증 방식**: 2.1.0 POM에는 Boot 버전이 명시되어 있지 않아 문서상 호환 여부는 확인하지 못했다. 대신 실제로 `bootRun`이 에러 없이 뜨는 것으로 확인했다.

### 3-2. Java 17 유지 (CLAUDE.md는 원래 21)
- **선택**: Java 17
- **이유**: Boot 4도 Java 17 이상이면 동작하므로 21로 올려야 할 기술적 이유가 없었다. 처음에 21을 권한 것은 CLAUDE.md 표기를 따랐을 뿐이다. 설치된 JDK도 17.0.2였다.
- CLAUDE.md는 17로 맞춰져 있음

### 3-3. Flyway 도입, `ddl-auto: validate`
- **선택**: SQL 파일(`db/migration/V1__init_schema.sql`)로 스키마 관리, Hibernate는 검증만
- **이유**:
  - 초기에 쓰던 `ddl-auto: create`는 서버를 재시작할 때마다 테이블을 지운다.
  - `update`는 컬럼 삭제, 타입 변경, 부분 인덱스, enum 타입을 제대로 다루지 못한다.
  - 스키마는 앞으로 반드시 바뀌므로 변경 이력이 남는 Flyway가 맞다.
  - `validate`로 두면 엔티티와 스키마가 어긋났을 때 기동 시점에 바로 드러난다.
- **주의**: 적용된 `V1`은 체크섬을 검사하므로 수정하면 기동이 실패한다. 이후 변경은 `V2__...sql`로 추가한다.

### 3-4. ENUM은 PostgreSQL 네이티브 `CREATE TYPE`
- **선택**: `varchar + CHECK`가 아니라 `CREATE TYPE ... AS ENUM`
- **이유**: DB 레벨에서 타입 안정성이 더 강하다.
- **감수한 비용**: 엔티티의 모든 enum 필드에 `@Enumerated(EnumType.STRING)` + `@JdbcType(PostgreSQLEnumJdbcType.class)` + `@Column(columnDefinition = "타입명")`이 필요하다. 빠뜨리면 `varchar`와 enum 타입 불일치로 INSERT가 실패한다.
- **알아둘 점**: enum 값을 추가하려면 `ALTER TYPE ... ADD VALUE` 마이그레이션이 필요하다.

### 3-5. 스키마에 추가한 제약·인덱스 (명세에 없던 것)
| 항목 | 내용 | 이유 |
|---|---|---|
| `users.email` | `UNIQUE (email) WHERE deleted_at IS NULL` 부분 인덱스 | soft delete한 계정의 이메일로 재가입하려면 일반 UNIQUE로는 막힘 |
| 소셜 계정 | `UNIQUE (provider, provider_id)` | 같은 소셜 계정의 중복 가입 방지 |
| `user_levels` | `UNIQUE (user_id, concept_tag)` | 분야당 레벨 1개 보장 |
| `answers` | `UNIQUE (user_id, answered_date) WHERE deleted_at IS NULL` | `ALREADY_ANSWERED_TODAY`(409)를 앱 로직뿐 아니라 DB에서도 보장. 동시 요청 이중 제출도 차단 |
| `chat_messages` | `(answer_id, id)` 인덱스 | ULID가 시간순이라 대화 순서 조회에 그대로 사용 |
| `answers` 부분 인덱스 | `feedback_viewed_at` WHERE `FEEDBACK_READY` | 1분 주기 이탈 처리 스케줄러가 대상만 빠르게 찾도록 |
| 기본값 | `created_at`, `updated_at`에 `DEFAULT now()` | JPA를 거치지 않는 INSERT도 안전 |

### 3-6. 다른 도메인 참조는 String ID 필드 (`@ManyToOne` 최소화)
- **선택**: `userId`, `questionId` 같은 `String` 필드. 같은 도메인 안(`AnswerFeedbackItem`·`ChatMessage` → `Answer`)만 `@ManyToOne(LAZY)`
- **이유**: CLAUDE.md의 "user_id 직접 참조(JOIN 없이 403 접근 제어)", "질문/답변 도메인 분리" 방침과 맞고, 패키지 간 의존이 생기지 않으며 지연 로딩·N+1 문제가 없다.

### 3-7. soft delete 조회는 Repository에서 명시적으로
- **선택**: 엔티티에 `@SQLRestriction`을 걸지 않고 `findByIdAndDeletedAtIsNull` 같은 쿼리로 명시
- **이유**: 계정 복구(soft delete의 목적)에는 삭제된 사용자를 조회할 수 있어야 한다. 전역 필터를 걸면 복구용 조회가 네이티브 쿼리로 우회해야 한다.
- **감수한 비용**: 조회할 때 `DeletedAtIsNull`을 빠뜨리면 삭제된 데이터가 노출될 수 있다. Repository 작성 시 주의.

### 3-8. BaseEntity 3분할
- **선택**: `BaseCreatedEntity`(createdAt) ← `BaseTimeEntity`(+updatedAt) ← `BaseSoftDeleteEntity`(+deletedAt)
- **이유**: 처음 만든 단일 `BaseEntity`는 세 컬럼을 전부 가정했는데, 실제 테이블은 `questions`, `chat_messages`, `answer_feedback_items`, `ai_usage_logs`처럼 `updated_at`이 없거나 `deleted_at`이 `users`·`answers`에만 있었다. 컬럼이 없는 테이블이 상속하면 `validate`에서 실패한다.
- **스키마 변경 한 가지**: `user_streaks`에 요청에 없던 `created_at`을 추가했다. 3개 클래스 중 `updated_at`만 가진 형태가 없어서, 엔티티가 따로 필드를 선언하는 것보다 `BaseTimeEntity`를 그대로 쓰는 편이 낫다고 판단했다.

### 3-9. ULID: `@IdGeneratorType` + monotonic
- **선택**: `@Ulid` 어노테이션 + `UlidGenerator`(Hibernate `BeforeExecutionGenerator`), `UlidCreator.getMonotonicUlid()`
- **이유**: PK 필드에 `@Ulid`만 붙이면 INSERT 시 자동 생성된다. monotonic을 쓰면 같은 밀리초 안에서도 생성 순서대로 정렬되어 채팅 메시지 순서가 보장된다. (스모크 테스트로 확인)

### 3-10. `.github/modernize/`는 `.gitignore`로 제외
- GitHub Copilot의 Java 업그레이드 기능이 만든 것으로 보이는 폴더. 프로젝트에 필요하지 않다고 보고 제외했다. (내용은 읽어보지 않음)

### 3-11. Swagger UI: springdoc 3.2.1, 운영 프로필에서는 비활성화
- **선택**: `springdoc-openapi-starter-webmvc-ui:3.2.1` 사용. `application-prod.yaml`에서 `springdoc.api-docs.enabled=false`, `springdoc.swagger-ui.enabled=false`.
- **이유(버전)**: springdoc 2.x는 Spring Boot 3 계열이고, 3.x가 Boot 4 대응 계열이다. Maven Central 목록에서 최신 3.2.1을 선택했다.
- **이유(운영 비활성화)**: API 문서는 엔드포인트와 요청 구조를 그대로 드러내므로 운영에서는 닫는 편이 안전하다. 기동 로그에도 "운영에서는 비활성화하라"는 경고가 나온다.
- **구성**: `OpenApiConfig`에 제목·버전, 서버 URL 2개(현재 서버 `/`, 운영 `https://api.anunjul.app`), Bearer JWT 보안 스키마를 등록했다. (서버 URL에 `/v1`을 넣지 않은 이유는 3-12 참고) Swagger UI의 Authorize 버튼에 Access Token을 넣으면 모든 요청에 Bearer 헤더가 붙는다.
- **`SecurityConfig`**: `/swagger-ui/**`, `/swagger-ui.html`, `/v3/api-docs/**`를 허용 목록 상수로 분리했다. 지금은 전체 허용이라 영향이 없지만, 인증을 적용할 때 Swagger가 같이 막히지 않게 하려는 것이다.
- **검증**: `local`에서 `/v3/api-docs`, `/swagger-ui.html`, `/swagger-ui/index.html`이 모두 200, `local,prod`에서는 모두 404. 컨트롤러가 아직 없어 `paths`는 비어 있는 것이 정상이다.

### 3-12. API 경로 `/v1` 접두사는 붙이지 않기로 함 + 로컬 포트 8081 고정
- **경위**: 처음에는 CLAUDE.md의 Base URL(`https://api.anunjul.app/v1`)을 따라 `WebMvcConfig`의 `addPathPrefix("/v1", ...)`로 접두사를 구현하고 임시 컨트롤러로 동작까지 확인했다. 그런데 `/v1`을 붙이기로 확정한 적이 없었다(유지 여부를 묻는 질문에 대한 답을 접두사 승인으로 잘못 해석). 이후 붙이지 않기로 결정하고 `WebMvcConfig`를 삭제했다.
- **`/v1`을 붙이지 않는 이유**: 클라이언트가 우리 프론트 하나뿐이라 API 버전 관리의 이점이 당장은 작고, MVP 단계에서 경로에 버전을 두는 것이 큰 의미가 없다.
- **감수한 비용**: 나중에 API를 깨는 변경이 필요해지면 `/v2`를 병행 운영하는 방식을 쓸 수 없어 별도 대응이 필요하다. 다시 붙이려면 `WebMvcConfig` 한 파일을 추가하면 되지만 프론트 호출부도 함께 바꿔야 한다.
- **CLAUDE.md 수정**: Base URL을 `https://api.anunjul.app`(`/v1` 없음)으로 고쳤다. 프론트와 협의된 값이었으므로 프론트에도 전달이 필요하다.
- **Swagger 서버 URL**: `/`(현재 접속 주소)와 `https://api.anunjul.app`. 로컬은 상대 경로라 포트가 바뀌어도 수정이 필요 없다.
- **참고(접두사를 쓸 경우의 함정)**: `addPathPrefix`로 접두사를 붙이면 API 문서의 경로 자체가 `/v1/...`로 생성되므로 서버 URL에 `/v1`을 또 넣으면 `/v1/v1/...`이 되어 "Try it out"이 깨진다. `server.servlet.context-path`는 Swagger 경로까지 바뀌어 맞지 않는다.
- **로컬 포트를 8081로 고정한 이유**: 8080은 이 PC에서 WSL 릴레이와 Docker Desktop이 점유한다. 포트를 그때그때 바꾸면 프론트 API 주소, CORS 설정, 문서가 계속 어긋나므로 고정했다. 값은 gitignore 대상인 `application-local.yaml`에 둔다. PC 환경에 따른 개인 설정이라 팀원과 운영에 영향이 없다.
- **검증**: 접두사 방식은 임시 컨트롤러로 확인 후 삭제했다(`/v1/ping` 200, `/ping` 404, 문서 경로 `/v1/ping`). 제거 후에는 컴파일과 기동으로 확인했다.

## 4. 겪은 문제와 해결 (트러블슈팅 소재)

### 4-1. Spring AI 1.0.0이 Boot 4.x와 맞지 않을 가능성 / 스타터 이름 변경
- **상황**: 요청서의 `spring-ai-openai-spring-boot-starter:1.0.0` + `spring-ai-bom:1.0.0`
- **문제**: 1.0.0은 Boot 3.x 계열 기준이고, 이 스타터 이름은 1.0.0 정식판에서 `spring-ai-starter-model-openai`로 바뀌었다. 그대로 쓰면 의존성 해석 실패 또는 기동 실패 위험.
- **해결**: Maven Central의 `maven-metadata.xml`에서 버전 목록을 조회 → 정식판 2.1.0 선택, 스타터 `spring-ai-starter-model-openai:2.1.0`의 POM 존재(HTTP 200)까지 확인.
- **한계**: POM만으로는 Boot 호환을 확정할 수 없어, `bootRun` 성공으로 최종 검증.
- **교훈**: 프레임워크 메이저 버전이 바뀌면 연관 라이브러리 버전과 아티팩트 이름을 먼저 확인할 것.

### 4-2. 8080 포트 충돌로 기동 실패
- **증상**: `APPLICATION FAILED TO START — Web server failed to start. Port 8080 was already in use.`
- **원인**: 다른 프로세스가 8080을 사용 중. 로그상 DB 연결, JPA, Spring AI 초기화는 모두 통과한 상태였다. 나중에 `Get-NetTCPConnection`과 프로세스 조회로 확인해 보니 점유 프로세스는 **`wslrelay.exe`(WSL 포트 릴레이)와 Docker Desktop(`com.docker.backend.exe`)** 이었다. 우리 앱이 아니라 개발 PC 환경 쪽이다.
- **해결**: 사용 중인 프로세스는 건드리지 않고 `--server.port=8081`로 확인용 기동.
- **교훈**: 기동 실패 로그는 끝까지 읽을 것. 앞부분이 모두 성공이면 원인은 포트 같은 환경 문제다. WSL이나 Docker Desktop을 쓰는 Windows 개발 PC에서는 8080이 이미 잡혀 있는 경우가 흔하다.
- **후속 조치**: 로컬 포트를 8081로 고정해 `application-local.yaml`의 `server.port`에 두었다. (3-12 참고)

### 4-3. DB 비밀번호가 커밋 대상 파일에 평문으로 있었음
- **상황**: `docker-compose.yml`과 `application.yaml` 기본값(`${DB_PASSWORD:iknewit}`)에 로컬용 비밀번호가 들어 있었다. git 연결 직전에 발견.
- **해결**:
  1. `docker-compose.yml`을 `${DB_NAME}`, `${DB_USERNAME}`, `${DB_PASSWORD:?...}`로 변경 (compose는 같은 폴더 `.env`를 자동으로 읽음)
  2. 랜덤 비밀번호를 `.env`와 `application-local.yaml`에만 기록 (둘 다 `.gitignore`)
  3. `application.yaml`에서 `DB_PASSWORD` 기본값 제거
  4. `.env.example`(비밀번호 비움)을 커밋 대상으로 추가
- **함정**: Postgres 비밀번호는 볼륨을 **처음 만들 때만** 적용된다. `.env`만 바꿔서는 기존 볼륨의 비밀번호가 안 바뀌므로 `docker compose down -v`로 볼륨을 지우고 다시 띄워야 했다. (당시 `ddl-auto: create` 단계라 잃을 데이터 없음)
- **git 히스토리**: 이미 커밋은 했지만 push 전이라 `git commit --amend`(여러 커밋이면 `reset --soft` 후 amend)로 옛 비밀번호를 히스토리에서 제거할 수 있었다. push 후였다면 히스토리 재작성 또는 저장소 재생성이 필요했을 것.
- **교훈**: 비밀 값은 첫 커밋 전에 분리한다. 한 번 push하면 지워도 히스토리에 남는다.
- **참고**: 이후 서버 실행 시 `--spring.profiles.active=local`(또는 `DB_PASSWORD` 환경변수)이 필요하다.

### 4-4. `git push` 403 — `Write access to repository not granted`
- **증상**: `fatal: unable to access 'https://github.com/i-knew-it/Backend.git/': The requested URL returned error: 403`
- **원인**: 코드나 설정 문제가 아니라 권한 문제. 로그인된 GitHub 계정이 조직(`i-knew-it`) 저장소에 쓰기 권한이 없었다.
- **점검 후보** (원인 후보로 안내한 것):
  1. Windows 자격 증명 관리자에 다른 계정의 `git:https://github.com` 자격 증명이 저장된 경우
  2. 조직 저장소의 Collaborators 권한 부족
  3. PAT의 `repo` 권한 또는 SAML SSO 승인 누락
- **해결**: 조직에서 쓰기 권한을 받은 뒤 push 성공.
- **교훈**: 403은 인증(401)이 아니라 인가 문제일 때가 많다. 먼저 어떤 계정으로 요청하고 있는지 확인할 것.

### 4-5. `PostgreSQLEnumJdbcType` import를 찾을 수 없음 (Hibernate 7.4 패키지 이동)
- **증상**: 엔티티 작성 직후 IDE에서 `The import org.hibernate.dialect.PostgreSQLEnumJdbcType cannot be resolved`
- **원인**: Hibernate 7.4에서 클래스 위치가 `org.hibernate.dialect.type.PostgreSQLEnumJdbcType`으로 바뀌었다. 기억에 의존해 옛 패키지를 썼고, 처음 안내한 경로도 틀렸다.
- **해결**: 추측하지 않고 Gradle 캐시의 `hibernate-core-7.4.15.Final.jar`를 `unzip -l`로 열어 실제 클래스 위치를 확인 → 9개 엔티티의 import를 `sed`로 일괄 수정.
- **교훈**: 메이저 버전이 올라간 라이브러리는 패키지 이동이 흔하다. 컴파일/IDE 오류가 나면 jar를 직접 확인하는 것이 가장 빠르다.

### 4-6. `validate`만으로는 부족 → 스모크 테스트로 INSERT 검증
- **문제의식**: `ddl-auto: validate`는 컬럼 존재와 타입을 검사할 뿐, 실제 INSERT에서 enum 캐스팅, ULID 생성, jsonb 직렬화, auditing이 동작하는지는 보장하지 않는다.
- **해결**: 임시 `@SpringBootTest` + `@Transactional`(롤백) 테스트로 `User`, `Question`, `Answer`, `AnswerFeedbackItem`, `ChatMessage`를 저장·조회했다. 확인한 것: ULID 26자 생성, enum 저장/조회, jsonb 저장/조회, `createdAt`/`updatedAt` 자동 채움, `timezone` 기본값, 같은 밀리초 메시지의 ID 정렬.
- **결과**: 통과 후 테스트 파일 삭제, DB 잔여 데이터 없음(롤백).
- **TODO**: 이 검증을 영구 테스트(Testcontainers 등)로 남길지 검토.

### 4-7. `compileJava` 실패 — `Failed to clean up stale outputs` / `Unable to delete directory build\classes\java\main`
- **상황**: Swagger 추가 후 `bootRun`으로 확인하려는데, 코드 오류 없이 컴파일 단계에서 실패했다. 몇 번 재시도해도 같았다.
  - 증상: `Failed to delete some children. This might happen because a process has files open or has its working directory set in the target directory.`
- **원인 추정**: `build/classes` 안의 파일을 다른 프로세스가 열고 있다. 이 프로젝트는 **OneDrive 폴더 안**에 있고 VS Code Java 확장(redhat.java)의 언어 서버도 떠 있어서, 동기화나 IDE 빌드가 파일을 잡았을 가능성이 가장 크다. 확정은 하지 못했다. (우리 앱 프로세스는 남아 있지 않았고, 명령행에 `iknewit`이 들어간 프로세스도 없었다.)
- **시도했다가 하지 않은 것**: 모든 `java.exe`를 강제 종료하는 방법은 IDE 언어 서버 등 무관한 프로세스까지 죽일 수 있어 사용하지 않았다. (실행 단계에서 차단되기도 했다.)
- **해결(검증용 우회)**: Gradle init script로 빌드 출력 디렉터리만 프로젝트 밖(스크래치 폴더)으로 돌려 `bootRun`했다. 프로젝트 파일은 수정하지 않았다.
  - `./gradlew -I redirect-build.init.gradle bootRun ...`
- **남은 문제**: 프로젝트의 `build/` 폴더는 여전히 잠겨 있을 수 있다. IDE의 Java 프로세스 정리 또는 OneDrive 동기화 일시 중지 후 `./gradlew clean`이 되는지 확인이 필요하다.
- **교훈**:
  - 이런 오류는 코드 문제가 아니라 파일 잠금이다.
  - 개발 프로젝트를 OneDrive 같은 동기화 폴더에 두면 `build/`, `.gradle/` 때문에 잠금이 생기기 쉽다. 가능하면 동기화 대상 밖으로 옮기는 것이 좋다.
  - 프로세스를 정리할 때는 이름이 아니라 PID와 명령행을 확인하고 필요한 것만 종료한다.

## 5. 앞으로 주의할 점

- **enum 필드**: `@Enumerated(STRING)` + `@JdbcType(PostgreSQLEnumJdbcType.class)` + `columnDefinition`을 항상 세트로. 새 필드는 기존 엔티티를 복사해서 작성.
- **`char(26)` PK/FK**: `@JdbcTypeCode(SqlTypes.CHAR)` + `@Column(length = 26)`. 안 붙이면 `validate`에서 `varchar`/`bpchar` 불일치가 날 수 있다.
- **`evaluationCriteria`**: 현재 `Map<String, Object>`라 JSON 객체일 때만 동작한다. 배열로 저장하려면 타입 변경 필요. 채점 기준 구조가 확정되면 DTO로 바꾸기.
- **Flyway**: 적용된 `V1`은 수정 금지, 변경은 `V2`로.
- **soft delete**: Repository에서 `DeletedAtIsNull`을 빠뜨리지 않기.
- **임시 `SecurityConfig`**: 전체 허용 상태. 인증 구현 때 교체하고 `/swagger-ui/**`, `/v3/api-docs/**` 허용 목록 포함.
