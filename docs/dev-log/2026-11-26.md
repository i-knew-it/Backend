## 2. 인증 구조 한눈에 보기

| 항목 | Access Token | Refresh Token |
|---|---|---|
| 형식 | JWT(HS256), claim: `sub`(userId), `type`, `jti`, `iat`, `exp` | 동일 |
| 만료 | 30분 | 7일 |
| 전달 | 응답 본문 | `HttpOnly; Secure; SameSite=Strict; Path=/auth` 쿠키 |
| 프론트 보관 | JS 메모리 | JS가 읽을 수 없음 |
| 서버 저장 | 안 함(검증만) | DB에 SHA-256 해시만 저장 (`refresh_tokens`) |

**엔드포인트** (모두 `/v1` 없음): `POST /auth/signup`, `/auth/login`, `/auth/token/refresh`, `/auth/logout`, `GET /auth/oauth2/authorize/google`, `/auth/oauth2/callback/google`, `GET /users/me`

**요청 흐름 요약**
- 보호된 API: 필터가 `Authorization: Bearer`를 검증 → 실패 사유(만료/무효)를 기록 → 인증이 필요한 경로면 EntryPoint가 `TOKEN_EXPIRED` / `TOKEN_INVALID` / `UNAUTHORIZED`로 401 응답
- 갱신: JWT 검증 → 해시로 DB 조회 → (폐기된 토큰이면 유예/탈취 판단) → 원자적 폐기 → 새 토큰 쌍 발급
- 소셜: 프론트가 `authorize`로 이동 → Google → 콜백 → 사용자 조회/생성 → Refresh 쿠키만 세팅하고 프론트로 리다이렉트 → 프론트가 `POST /auth/token/refresh`로 Access Token 수령

## 3. 결정 사항과 이유

### 3-1. Refresh Token은 원문이 아니라 SHA-256 해시로 저장
- **선택**: `refresh_tokens.token_hash char(64)`. 요청서의 `token varchar(512)`(원문 저장)에서 변경.
- **이유**: DB가 유출돼도 해시만으로는 토큰을 사용할 수 없다. 조회는 쿠키로 받은 토큰을 해시해 비교하면 되므로 기능 손실이 없다.
- **추가 컬럼**: `revoked_at`. Rotation으로 교체된 토큰을 삭제하지 않고 폐기 시각만 기록해야 재사용을 감지할 수 있다.

### 3-2. 토큰 만료 30분 / 7일 (CLAUDE.md의 15분 / 30일에서 변경)
- 요청된 값으로 변경하고 `application.yaml`(`jwt.*`)에서 한 곳으로 관리. CLAUDE.md도 함께 수정했다.
- Access Token을 짧게 두는 이유: stateless라 발급 후 서버가 취소할 수 없어, 탈취 시 피해 시간을 제한하려는 것이다.

### 3-3. Rotation + 재사용 감지 + 유예 10초
- **Rotation**: 갱신할 때마다 Refresh Token을 교체한다. 한 번 쓴 토큰은 다시 못 쓰게 해서 탈취를 탐지한다.
- **재사용 감지**: 이미 폐기된 토큰이 다시 오면 그 사용자의 모든 토큰을 삭제한다. 공격자가 훔친 토큰을 먼저 쓰면 정상 사용자의 다음 갱신이 실패하면서 탈취가 드러나고, 공격자가 가진 새 토큰도 함께 무효가 된다.
- **유예 10초를 둔 이유(설계 문제)**: Access Token이 만료되는 순간 화면이 API를 여러 개 동시에 부르면 모두 401을 받고 각자 갱신을 요청한다. 브라우저 탭이 여러 개여도 같다(쿠키 공유). 이때 같은 Refresh Token이 겹쳐 오면 정상 사용자가 탈취범으로 오인되어 로그아웃된다. 프론트가 갱신을 한 번에 하나만 보내도 **탭 사이는 조율이 어려워** 서버에서 유예를 두었다.
- **감수한 비용**: 탈취된 토큰이 있다면 교체 직후 10초 동안은 쓸 수 있다.
- **원자적 폐기**: `UPDATE ... WHERE token_hash=? AND revoked_at IS NULL`로 폐기하고 영향 행 수가 0이면 "방금 다른 요청이 먼저 처리"로 보고 그 폐기 시각으로 유예를 판단한다.
- **`noRollbackFor`**: 재사용 감지에서 "전체 삭제 후 예외"를 던지는데, 기본 설정이면 예외로 삭제까지 롤백되어 감지가 무의미해진다.

### 3-4. 단일 디바이스 로그인 (처음 설계는 멀티 디바이스)
- **선택**: 새 로그인(가입, 이메일, 소셜)이 성공하면 그 사용자의 기존 Refresh Token을 모두 삭제한다.
- **동작**: 이전 기기는 Access Token(최대 30분)이 만료되어 갱신을 시도할 때 로그아웃된다.
- **즉시 끊지 않은 이유**: 즉시 끊으려면 Access Token마다 DB를 확인해야 해서 stateless의 이점을 잃는다.
- **주의**: Rotation 시에는 기존 행을 지우지 않는다. 지우면 폐기된 토큰의 재사용을 감지할 수 없어, 탈취자가 새 토큰을 쥔 채로 남게 된다. 삭제는 새 로그인 때만 한다.
- **남은 정합성 문제**: `user_fcm_tokens`는 여전히 멀티 디바이스 구조라 이전 기기에도 알림이 갈 수 있다. 알림 구현 때 정책을 정해야 한다.

### 3-5. 무차별 대입 방어
- **로그인**: 같은 "이메일 + IP"에서 5회 연속 실패 시 15분 차단(429, `Retry-After`).
- **IP**: 같은 IP에서 로그인·가입 합산 분당 20회.
- **이메일만이 아니라 IP까지 키로 쓴 이유**: 이메일만으로 차단하면 남의 계정을 일부러 잠그는 공격(계정 잠금 DoS)이 가능하다. IP를 키에 넣으면 본인은 다른 IP에서 로그인할 수 있다.
- **차단 중에는 비밀번호가 맞아도 거절**하고, 차단된 요청은 실패로 세지 않아 차단 시간이 계속 늘어나지 않는다.
- **구현**: Caffeine 인메모리. EC2 한 대 MVP에는 충분하지만 **재시작하면 초기화**되고 서버가 여러 대면 공유되지 않는다(확장 시 Redis 등). 항목 수는 10만 개로 제한(메모리 고갈 방지).
- **로그인 실패 응답은 동일**: 없는 이메일, 틀린 비밀번호, 소셜 전용 계정 모두 `INVALID_CREDENTIALS`. 없는 이메일에도 더미 해시로 bcrypt 비교를 해서 응답 시간 차이로 이메일 존재 여부를 알아내는 공격을 줄였다.
- **Nginx 뒤에서는** `server.forward-headers-strategy` 설정이 필요하다. 없으면 모든 요청이 프록시 IP로 보여 IP 제한이 모두에게 걸린다. 배포 단계 TODO.

### 3-6. 갱신 실패 시 쿠키 만료 + 만료 행 자동 정리
- **쿠키 만료**: 죽은 쿠키를 브라우저가 계속 보내는 것을 막는다. **유예 시간과 짝**이어야 한다. 유예가 없으면 동시 요청 중 하나가 실패하며 내려주는 "쿠키 삭제"가 다른 요청이 받은 유효한 새 쿠키를 지워 사용자가 로그아웃된다.
- **정리 스케줄러**: 매일 03:00(KST)에 `expires_at`이 지난 행 삭제. 폐기된 행도 재사용 감지에 필요하므로 만료 전에는 남기고, 만료와 함께 정리된다. 규모는 기기당 7일 기준 수백 행 정도로 작다.

### 3-7. 닉네임: `name`을 `nickname`으로 이름 변경 (V3)
- **선택**: 새 컬럼을 더하지 않고 기존 `name`을 `nickname`으로 변경. 사용자를 닉네임으로 부르는 용도라 실명을 따로 받지 않는다.
- **규칙**: 2~20자, 한글(완성형)·영문·숫자·`_`. **중복 허용**(개인 학습 서비스라 불필요, 팀 순위 기능이 생기면 재검토). `ㅋㅋ` 같은 자모만 있는 값은 거부.
- **소셜 가입**: Google 이름에서 허용되지 않는 글자를 제거해 규칙에 맞추고, 쓸 수 있는 글자가 부족하면 `사용자1234` 형태로 대체.
- 적용된 `V1`은 수정할 수 없어 `V3` 마이그레이션으로 처리했다.

### 3-8. 비밀번호 규칙과 확인란
- 8~72자, 영문 대문자·소문자·숫자·특수문자 각 1개 이상, 공백 불가.
- **특수문자는 ASCII 기호로 한정**: `[^A-Za-z0-9]`로 두면 한글이 "특수문자"로 인정되는 허점이 생긴다.
- **72바이트 검증을 따로 둔 이유**: bcrypt는 72바이트까지만 반영하고, 한글은 글자당 3바이트라 25자만 넘어도 걸린다. 글자 수 검증만으로는 놓친다.
- `passwordConfirm` 일치는 서버에서도 검사(API를 직접 호출해도 일관되도록). 로그인에는 이 규칙을 적용하지 않는다.
- 참고: 최신 지침은 복잡도 규칙보다 **길이**가 더 효과적이라고 본다. 최소 길이를 10자 이상으로 올리는 것도 검토할 만하다.

### 3-9. 소셜 로그인: 쿠키만 세팅하고 프론트로 리다이렉트 (Access Token을 URL에 싣지 않음)
- **요청**은 Access Token을 쿼리 파라미터로 전달하는 방식이었으나 변경했다.
- **이유**: URL은 브라우저 기록, 서버·프록시 로그, `Referer` 헤더로 새기 쉽고, "Access Token은 JS 메모리" 원칙과도 어긋난다. 대신 Refresh 쿠키만 세팅하고 프론트가 `POST /auth/token/refresh`로 Access Token을 받는다.
- **Google만 먼저**: 카카오는 사용자 정보 구조가 달라 이후 `OAuth2UserInfoFactory`에 분기를 추가한다. 요청했던 커스텀 `OAuth2UserService`는 Google만 지원하는 지금은 불필요해서 만들지 않았다.
- **스코프 `profile, email`(openid 제외)**: 일반 OAuth2(userinfo 조회)로 처리해야 카카오도 같은 경로로 붙일 수 있다.
- **`email_verified`가 true인 계정만 허용**: 미인증 이메일로 남의 계정을 가로채는 것을 막는다.
- **같은 이메일의 일반 계정이 있으면 자동 연동하지 않음**: 이메일만 믿고 연동하면 계정 탈취에 악용될 수 있다. 프론트로 `EMAIL_ALREADY_EXISTS`를 알린다.
- **프론트 약속**: 성공 `{FRONTEND_URL}/auth/callback`, 실패 `{FRONTEND_URL}/login?error=코드`(`EMAIL_ALREADY_EXISTS`, `EMAIL_NOT_VERIFIED`, `OAUTH_FAILED`). 실패 원인(access_denied 등)은 서버 로그에만 남기고 프론트에는 일반 코드만 전달. 리다이렉트 대상은 서버 설정값이라 요청으로 바뀌지 않는다(오픈 리다이렉트 방지).
- **`state` 저장**은 Spring 기본(세션)을 그대로 쓴다. 코드가 단순하고 EC2 한 대에서는 문제가 없다. 서버를 여러 대로 늘리면 쿠키 저장 방식으로 바꿔야 한다.

### 3-10. 에러 응답과 CORS
- **형식**: `{"error":{"code","message"}}`, 서버가 `message`를 직접 제공. 추가한 코드: `VALIDATION_ERROR`(400), `UNAUTHORIZED`(401), `FORBIDDEN`(403), `TOO_MANY_REQUESTS`(429). 요청서의 `ALREADY_EXISTS`는 CLAUDE.md와 맞춰 `EMAIL_ALREADY_EXISTS`로 통일.
- **CORS(요청에 없던 것)**: 쿠키 인증은 `allowCredentials=true`와 정확한 origin이 필수라 추가. 허용 origin은 환경변수 `FRONTEND_URL`. `Retry-After`를 프론트(JS)가 읽도록 노출.
- **CSRF 끔**: JWT(Authorization 헤더) 기반이고, 쿠키를 쓰는 갱신 엔드포인트는 `SameSite=Strict`로, 소셜 로그인은 `state` 파라미터로 막는다.

### 3-11. 내 정보 조회 `GET /users/me` 추가
- **왜 필요했나**: `POST /auth/token/refresh` 응답에는 `accessToken`만 있고 `user`가 없다. 가입/로그인 응답의 `user`는 프론트 메모리와 함께 새로고침하면 사라지므로, **새로고침 후**(이메일 로그인 포함)와 **Google 로그인 직후**(가입/로그인 응답을 거치지 않음)에는 닉네임 등 사용자 정보를 얻을 방법이 없었다. 온보딩 완료 여부(`onboardingCompleted`)로 화면을 분기하는 데도 필요하다.
- **두 방안 중 선택**: (A) `GET /users/me` 구현, (B) `refresh` 응답에 `user` 포함. A를 택했다. CLAUDE.md 명세에 이미 있고, 설정 화면·닉네임 변경 등 이후 기능에도 어차피 필요하기 때문이다. 흐름은 앱 시작/소셜 콜백 모두 `refresh` → `me` 순서.
- **응답**: `id, email, nickname, provider, onboardingCompleted, timezone`. 비밀번호 해시, `providerId`, 삭제 시각 같은 내부 값은 노출하지 않는다(테스트로 확인).
- **본인만 조회**: 경로에 사용자 ID를 받지 않고 토큰의 userId만 사용하므로 다른 사람의 정보를 볼 수 없다.
- **탈퇴(soft delete)한 계정의 토큰**: Access Token은 DB를 확인하지 않아 유효기간(최대 30분)이 남아 있을 수 있다. 이 API는 DB를 조회하므로 이 경우 401 `TOKEN_INVALID`를 준다. 첫 번째 "인증이 필요한 실제 API"라 JWT 필터와 `@AuthenticationPrincipal` 흐름이 실제로 동작함도 함께 확인했다.

### 3-12. CodeRabbit 리뷰 설정 (`.coderabbit.yaml`)
- **목적**: PR마다 보안·설계 규칙(soft delete, 단일 디바이스, Flyway 수정 금지 등)을 사람 대신 한 번 더 점검하게 한다. 팀 Git 규칙에 "CodeRabbit이 `develop` 대상 PR을 자동 리뷰"가 있어 백엔드 저장소에도 같은 설정을 넣었다.
- **초안의 문제와 수정**: 처음 작성된 설정을 읽어 보니 그대로는 지침이 거의 적용되지 않을 상태였다.
  1. **경로 패턴 불일치**: 이 프로젝트는 도메인별 패키지(`auth/`, `user/`, `answer/` ...)라서 `**/entity/**`, `**/service/**`, `**/controller/**`, `**/repository/**` 같은 폴더가 없다. 그대로 두면 `config/`, `auth/`, `db/migration/`, `test/` 규칙만 매칭된다. → **파일 이름 기준**(`*Controller`, `*Service`, `*Repository`, `*Scheduler`)으로 바꿨다.
  2. **`develop` 자동 리뷰 설정 누락**: CodeRabbit은 기본적으로 기본 브랜치(`main`) 대상 PR만 자동 리뷰한다. → `reviews.auto_review.base_branches: [develop]` 추가.
  3. **오래된 내용**: "V1은 수정 금지, 변경은 V2부터"는 이미 V1~V3이 있어 맞지 않는다. → "이미 머지된 마이그레이션은 수정 금지, 다음 번호로 추가"로 변경.
  4. **규칙 위치**: "AI에 PII 미전달"은 인증이 아니라 AI 연동 규칙이라 `auth/`에서 `ai/`로 옮겼다.
- **지침 보강**: 현재 구현·결정을 반영해 추가했다(엔티티의 `@Ulid`·Base 클래스 선택, `@Modifying` flush/clear, 롤백되면 안 되는 쓰기의 `noRollbackFor`, 경로에 `/v1` 접두사 금지, Swagger 어노테이션, 단일 디바이스 정책, 소셜 로그인 규칙, 리다이렉트 URL에 토큰 금지).
- **엔티티는 이름을 나열**: 엔티티는 파일 이름에 공통 규칙이 없어서 14개 이름을 중괄호 패턴으로 적었다. **새 엔티티를 만들면 목록에도 추가해야 한다.** 번거로우면 엔티티를 `entity` 하위 패키지로 옮기는 방법이 있다.
- **검증**: YAML 문법을 파싱했고, 각 패턴이 실제 파일에 매칭되는지 확인했다(엔티티 14개가 실제 엔티티와 일치, Controller 3, Service 3, Repository 2, Scheduler 1, auth 27 등). `sse/**`는 아직 코드가 없어 0개이고, 채팅 구현 때부터 적용된다.
- **확인하지 못한 것**: 중괄호(`{A,B}`) 패턴을 CodeRabbit이 지원하는지, 앱이 이 저장소에 설치되어 있는지는 실제 PR로만 알 수 있다. 설정을 처음 넣는 PR #5에는 리뷰가 달리지 않았다(설정이 적용되기 전이라 예상된 결과).

## 4. 겪은 문제와 해결 (트러블슈팅 소재)

### 4-1. JWT로 인증된 요청마다 세션(JSESSIONID)이 생김 ← 가장 중요
- **상황**: 소셜 로그인 `state` 저장에 세션이 필요해서 세션 정책을 `IF_REQUIRED`로 바꿨다.
- **발견**: 테스트 "JWT 인증은 세션을 만들지 않는다"가 실패했다. 가입 요청은 세션이 없는데, **Access Token으로 호출한 보호된 API 요청에는 세션이 있었다.**
- **원인**: `IF_REQUIRED`에서는 `SessionManagementFilter`가 "요청 도중 인증이 생겼다"고 보고 그 인증 정보를 세션에 저장한다. 우리 JWT 필터가 `SecurityContext`를 직접 세팅했기 때문이다. 실제 서버라면 인증된 API 호출마다 `JSESSIONID`가 발급되어 세션이 쌓인다(메모리 증가, 불필요한 쿠키).
- **해결**: `STATELESS`로 되돌렸다. 소셜 로그인의 `state`는 Spring이 `request.getSession()`으로 직접 세션을 만들어 `STATELESS`여도 동작한다.
- **검증**: 인가 시작 테스트에서 `state`가 세션에 저장되는지 확인하고, 실제 서버에서 인증된 호출에 `Set-Cookie`가 없는 것을 봤다. 인가 시작 응답에는 `JSESSIONID`가 `HttpOnly; SameSite=Lax`로 내려간다. 마지막으로 브라우저로 Google 로그인을 직접 해서 end-to-end도 확인했다.
- **교훈**: "인증은 stateless, OAuth 핸드셰이크만 세션"을 원하면 세션 정책은 `STATELESS`로 두고 Spring의 OAuth 세션 사용에 맡긴다. 자동 테스트가 잡아준 문제이므로 "세션이 생기지 않는다"를 테스트로 남겨 두었다.

### 4-2. 같은 Refresh Token 동시 요청 → 정상 사용자가 로그아웃되는 문제 (설계)
- **상황**: Rotation을 단순하게 구현하면, Access Token 만료 순간 동시에 날아온 갱신 요청 중 두 번째부터 "재사용"으로 판정된다.
- **대응**: 유예 10초 도입(3-3). 쿠키 만료 처리와 함께 설계해야 서로의 부작용이 없다(3-6).
- **테스트**: 유예 안의 재사용은 허용, 유예 후(폐기 시각을 1분 앞당겨 재현)의 재사용은 전체 무효화되는 것을 확인.

### 4-3. 앞뒤 공백이 있는 이메일 테스트가 400
- **증상**: "공백을 무시하고 중복을 막는다" 테스트가 409를 기대했는데 400.
- **원인**: 코드 문제가 아니라 기대값 문제. `@Email` 검증이 공백이 있는 이메일을 먼저 거부한다.
- **결정**: 검증을 엄격하게 두고 테스트를 실제 동작에 맞췄다(대소문자 중복은 409, 앞뒤 공백은 400).

### 4-4. Windows 셸에서 curl로 한글을 보내면 400
- **증상**: 실제 서버에 curl로 가입 요청 시 한글 닉네임이 있으면 `VALIDATION_ERROR`(일반 메시지).
- **원인**: 서버 문제가 아니라 셸이 한글을 UTF-8이 아닌 코드페이지로 보내 JSON 파싱이 실패했다. MockMvc 테스트에서는 한글이 정상.
- **해결**: 확인용 요청에서는 한글을 `\uXXXX` 이스케이프(ASCII)로 보냈다.

### 4-5. IDE에서 `cannot be resolved` 오류가 반복
- 새 의존성(OAuth2 스타터, springdoc)을 추가하면 IDE가 Gradle을 다시 불러오기 전까지 빨간 줄이 생기지만 실제 빌드와 테스트는 통과한다. Gradle 프로젝트 새로고침으로 해결. 컴파일 결과를 기준으로 판단한다.

### 4-6. 프로젝트 `build/` 폴더 잠금 (전날 4-7과 이어짐)
- OneDrive 폴더 안이라 계속 영향이 있어, 빌드 출력만 프로젝트 밖으로 돌리는 Gradle init script로 검증했다. 근본 해결(프로젝트를 OneDrive 밖으로 이동)은 아직 미실시.

### 4-7. 브랜치 전략과 실제 상태의 불일치 (git 규칙을 공유받은 뒤 발견)
- 팀 규칙은 `develop` 기준(`main` 직접 커밋 금지, 작업 브랜치는 `develop`에서 따서 `develop`으로 PR)인데, 저장소에는 `develop`이 없었다. 첫 PR(#1)은 `main`으로 머지됐고, 인증 작업은 `feat/health-check` 위에서 진행됐다.
- **정리**: `main`에는 PR #1(스키마·엔티티·Swagger)과 PR #2(health-check)가 이미 머지되어 있어서, 그 시점의 `main`에서 `develop`을 만들어 원격에 올리고, `develop`에서 `feat/auth`를 땄다. 커밋 전 변경 사항은 브랜치를 옮겨도 그대로 따라온다. PR #1이 `main`으로 머지된 것은 되돌리지 않았다. 이후 PR은 모두 `develop`으로 올린다.
- **규칙 문서화**: 공유받은 Git 규칙(브랜치 전략, 타입, 커밋 메시지, PR 형식, 라벨)을 CLAUDE.md의 "Git 규칙" 섹션에 추가했다.
- **겪은 혼선**: 처음 상태를 확인할 때 로컬에 남은 **마지막 fetch 기준의 정보**로 "health-check가 머지되지 않았다"고 잘못 판단했다. 사용자가 `git fetch` 후 `git log origin/main`으로 PR #2 머지를 확인해 바로잡았다.
- **교훈**: 원격 상태를 판단할 때는 먼저 `git fetch`를 하고 `origin/*`를 확인한다. 로컬의 `origin/*`는 마지막 fetch 시점의 기록일 뿐이다.
- **다시 커밋할 때의 주의**: `feat/auth`가 이미 푸시되어 있으므로, 추가 작업(`/users/me`)은 `amend`하지 않고 새 커밋으로 올린다(amend는 강제 푸시가 필요함). PR은 하나로 유지한다.
- **결과**: `feat/auth`는 PR #4로 `develop`에 머지됐고, 이후 `chore/coderabbit`(PR #5), `docs/dev-log-coderabbit`도 모두 `develop`에서 땄다.

### 4-8. `git switch develop` 중 `Deletion of directory '...' failed. Should I try again? (y/n)`
- **상황**: 머지가 끝난 뒤 정리하려고 `chore/coderabbit`에서 `git switch develop`을 했더니 `src/main/java/com/example/iknewit/auth/dto` 삭제 실패 프롬프트가 떴다.
- **원인 1 — 로컬 `develop`이 오래됨**: 로컬 `develop`은 처음 만들 때(`main`에서 분기, `feat/auth` 머지 전)의 상태로 남아 있었다. 그 브랜치로 전환하면 Git이 `develop`에 없는 파일(인증 코드 등)을 작업 폴더에서 지우려고 한다.
- **원인 2 — 폴더 잠금**: 파일은 지웠지만 폴더 자체를 다른 프로그램이 잡고 있어 삭제가 실패했다. 프로젝트가 OneDrive 폴더 안이라 `build/` 폴더 잠금(4-6)과 같은 종류로 보이며, OneDrive 동기화나 IDE, 터미널이 폴더를 연 상태였을 가능성이 크다(정확한 주체는 확인하지 못함).
- **대응**: `n`을 입력해 빈 폴더만 남기고 전환을 계속한 뒤 바로 `git pull`로 `develop`을 최신으로 올려 지워졌던 파일을 복구하고, `git status`가 깨끗한지 확인한다. Git은 빈 폴더를 추적하지 않아 영향이 없다. `pull` 전에는 서버 실행·빌드·테스트를 하지 않는다(인증 코드가 잠깐 없는 상태).
- **예방**: 로컬 `develop`을 거치지 않고 원격 기준으로 바로 브랜치를 만든다.
  - `git fetch origin` → `git switch -c 새브랜치 --no-track origin/develop`
  - 로컬 `develop`만 갱신하려면 `git fetch origin develop:develop` (브랜치를 옮기지 않고 앞으로 당김)
- **교훈**: 머지가 끝난 브랜치 정리나 새 작업 시작은 항상 `fetch` 후 `origin/develop` 기준으로 한다. 오래된 로컬 브랜치로 전환하면 작업 폴더가 크게 바뀌고, 그만큼 파일 잠금 문제를 만날 가능성도 커진다. 프로젝트를 OneDrive 밖으로 옮기는 것(남은 일)이 근본 해결이다.

## 5. 검증 결과

- **자동 테스트 88개 통과** (단위 + 통합, 로컬 DB 필요): JWT, 닉네임, 요청 제한기(시간 제어), 가입·로그인·갱신·로그아웃, 단일 디바이스, 유예·재사용, 쿠키 속성, 보호 경로의 401 세 종류, CORS, 무차별 대입, 소셜 서비스·핸들러·인가 시작 리다이렉트, 정리 스케줄러, `/users/me`(이메일·Google 사용자, 내부 값 미노출, 토큰 종류별 401, 탈퇴 계정).
- **실제 HTTP**: 인가 시작 302(PKCE 포함), 가입 201과 쿠키 속성, 인증된 호출에 세션 쿠키 없음, 비밀번호 규칙·확인 불일치 400, 두 번째 로그인 뒤 이전 토큰 401과 쿠키 만료, 5회 실패 후 429와 `Retry-After`.
- **Google 실제 로그인(브라우저)**: 로그인 후 `{FRONTEND_URL}/auth/callback`으로 돌아오고 `refreshToken` 쿠키(HttpOnly, Secure, Path=/auth, Strict)가 세팅됨. DB에 `provider=GOOGLE` 사용자가 생성되고 `refresh_tokens` 활성 행이 1개. 프론트가 아직 없어 callback 페이지 자체는 열리지 않는 것이 정상.
- **자동화가 불가능한 구간**: Google과 코드→토큰을 주고받는 부분은 실제 계정으로만 확인 가능. 이번에 수동 확인함.
