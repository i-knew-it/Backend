## 2. 결정 사항과 이유

### 2-1. 로그인도 사용자 행을 잠그고 조회한다
- **문제 시나리오(리뷰 지적)**: 공격자가 알고 있는 옛 비밀번호로 로그인하는 동안 본인이 비밀번호를 재설정하는 경우다.
  1. 로그인이 사용자를 **잠금 없이** 읽는다(옛 비밀번호 해시).
  2. 그 사이 재설정이 새 비밀번호를 저장하고 **모든 세션을 삭제**한 뒤 커밋한다.
  3. 로그인은 bcrypt 비교(약 0.1초)를 끝내고 옛 해시 기준으로 통과해서 **재설정이 끝난 뒤에 새 세션을 만든다.**
  - 결과적으로 "재설정하면 모든 기기가 로그아웃된다"는 약속이 깨진다. 옛 비밀번호로 만든 세션이 살아남는다.
- **선택**: 로그인이 `SELECT ... FOR UPDATE`로 사용자 행을 잠그고 조회한 뒤 비밀번호를 비교한다. 로그인이 먼저면 재설정이 그 세션까지 지우고, 재설정이 먼저면 로그인이 기다렸다가 **새 해시**를 읽어서 옛 비밀번호가 거절된다.
- **부수 효과 — 단일 디바이스 정책이 동시 로그인에서도 지켜진다**: 같은 사용자의 로그인 3개를 동시에 보냈더니 수정 전에는 Refresh Token이 **3개** 남았다("기존 토큰 삭제 → 새 토큰 저장"이 뒤섞임). 정책 구현에 있던 구멍이다.
- **감수한 비용**: 같은 사용자의 로그인이 사용자 행 잠금 때문에 한 번에 하나씩 처리된다(bcrypt 시간만큼). 가입되지 않은 이메일은 잠글 행이 없어 그대로 진행되고 응답은 같다. 같은 사용자를 노린 반복 시도는 기존 제한(IP당 분당 20회, 연속 실패 5회)이 막는다.

### 2-1-1. 오답 로그인은 잠금을 잡지 않는다 (리뷰 3차 반영)
- **문제**: 2-1처럼 로그인이 무조건 사용자 행을 잠그면, 남의 이메일로 **오답 로그인**을 반복해도 그 사용자의 정상 로그인·재설정이 줄을 선다. 대기하는 요청은 DB 커넥션도 쥐고 있어서(풀 기본 10개) 여러 IP로 분산하면 다른 사용자 요청까지 커넥션을 못 받을 수 있다.
- **수정**: ① 잠금 없이 해시 **문자열만** 조회해 비밀번호를 비교하고, 틀리면 바로 거절한다. ② 맞은 경우에만 사용자 행을 잠그고 **최신 해시로 다시 비교**한 뒤 같은 트랜잭션에서 세션을 만든다. 그 사이 재설정으로 해시가 바뀌었으면 거절된다.
- **함정**: 1차 조회를 엔티티로 하면 영속성 컨텍스트에 남아 잠금 조회가 오래된 해시를 그대로 돌려준다. 그래서 1차 조회는 값(`findPasswordHashByEmail`)만 읽는다.
- **비용**: 성공 로그인은 bcrypt를 두 번 계산한다(약 0.1초 추가). 실패 경로는 그대로다.
- **검증**: "다른 트랜잭션이 잠금을 쥔 동안 오답 로그인이 3초 안에 401" 테스트 추가. 1단계를 빼면 이 테스트가, 2단계 재검증을 빼면 기존 재설정 경쟁 테스트가 실패함을 확인한 뒤 복구했다.

### 2-2. `Retry-After`는 "윈도우 전체"가 아니라 "남은 시간"
- **문제**: 한도를 넘기면 항상 윈도우 전체(재설정 3600초, IP 60초)를 돌려줬다. 윈도우는 첫 요청 시각부터 고정이라 59분이 지났어도 "1시간 뒤"라고 알려 줬다. 프론트가 이 값으로 버튼을 막으면 필요 이상으로 오래 막는다.
- **지적은 재설정만이었지만 IP 제한도 같은 문제**라서 함께 고쳤다.
- **수정**: 카운터와 함께 윈도우 시작 시각을 저장하고, 남은 시간을 **초 단위로 올림**(최소 1초)한다. 0초로 내려가면 클라이언트가 바로 다시 시도해서 또 차단된다. 횟수를 올리는 것은 캐시 쓰기가 아니라서 조회만으로 윈도우가 늘어나지 않는다(차단된 요청을 계속 보내도 남은 시간은 처음 시작 시각 기준으로 줄어든다).
- **올림 계산 보정(리뷰 5차)**: 처음에는 `toMillis()`로 밀리초까지 자른 뒤 올려서, 남은 시간이 1.0005초면 1초로 계산됐다(올림이면 2초). 초와 나노초 잔여분을 그대로 쓰는 `ceilSeconds` 한 곳으로 모으고 로그인 차단(`checkLogin`)의 같은 계산도 함께 고쳤다. 영향은 1밀리초 미만 구간이라 작지만 수정 비용도 작아 반영했다. 1.2초→2, 1.0005초→2, 정확히 1초→1, 1나노초→1 경계를 테스트하고, 옛 계산으로 되돌리면 실패함을 확인했다.
- 시계를 조작하는 단위 테스트로 "즉시 → 3600", "30분 뒤 → 1800", "만료 1초 전 → 1", "남은 1.2초 → 2", "차단 요청을 반복해도 연장되지 않음", IP는 "60 → 35 → 1"을 검증한다.

### 2-3. `refresh`도 사용자 행을 잠근다 (리뷰 4차 반영, 기존 결론 정정)
- **처음 결론(틀림)**: 갱신과 로그인·재설정을 동시에 보내는 테스트에서 교착이 재현되지 않았고, Hibernate가 `for no key update`를 쓰므로 외래키 검사와 충돌하지 않는다는 이유로 "`refresh`는 잠그지 않아도 안전"하다고 결론냈다. 이는 **교착만 따진 결론**이었다.
- **놓친 문제(리뷰 지적)**: 갱신이 기존 토큰을 UPDATE해 행 잠금을 쥔 사이에 로그인이 "사용자 토큰 전부 삭제"를 실행하면 갱신 커밋까지 기다린다. PostgreSQL READ COMMITTED에서 이 DELETE는 **시작 시점 스냅샷** 기준이라, 갱신이 그 뒤에 넣고 커밋한 새 토큰은 지우지 못한다. 결과적으로 로그인의 토큰과 갱신의 새 토큰이 둘 다 남아 단일 디바이스 정책이 깨진다. `revoke`만 손봐서는 해결되지 않는다.
- **재현**: 갱신과 같은 순서(토큰 UPDATE → 1.5초 뒤 INSERT → 커밋)를 트랜잭션으로 만들고 그 사이에 로그인을 보내니 토큰이 **2개** 남았다.
- **기존 테스트가 못 잡은 이유**: 로그인이 DELETE 전에 bcrypt를 두 번(약 0.2초) 돌아서 갱신(수 ms)이 항상 먼저 끝난다. 통과한 것이 안전하다는 증거가 아니었다.
- **수정**: `refresh`가 서명 검증을 통과한 뒤 JWT의 `userId`로 사용자 행을 먼저 잠근다(`findByIdForUpdate`). 로그인·재설정과 같은 "사용자 행 → 토큰 행" 순서라 서로 직렬화되고 교착도 없다. 위조 토큰은 서명 검증에서 걸러지므로 잠금을 잡지 못한다.
- **검증**: "다른 트랜잭션이 사용자 행 잠금을 쥔 동안 갱신이 1초 뒤에도 끝나지 않고, 풀리면 끝난다" 테스트 추가(로그인과 갱신이 겹치는 순간은 직접 만들 수 없어 잠금 직렬화를 결정적으로 검증). 잠금을 빼면 이 테스트가 실패함을 확인했다.
- **교훈**: "교착이 없다"와 "동시에 와도 결과가 맞다"는 다른 질문이다. 동시성 테스트가 통과해도 타이밍을 실제로 만들어 봤는지 확인해야 한다.

## 3. 겪은 문제와 해결 (트러블슈팅 소재)

### 3-1. 경쟁 상태 재현이 처음에는 실패했다 → 시작 시점을 조금씩 어긋나게
- **상황**: "옛 비밀번호 로그인과 재설정을 동시에 시작"하는 테스트를 수정 전 코드로 20라운드 돌렸는데 **전부 통과**했다. 리뷰 지적이 틀린 줄 알 뻔했다.
- **원인**: 두 작업을 같은 순간에 시작하면, 재설정이 단계가 더 많아서 항상 로그인보다 늦게 끝난다. 그래서 재설정의 세션 삭제가 로그인이 만든 세션까지 쓸어 버려 버그가 드러나지 않았다. 버그는 "로그인이 재설정 커밋 직전에 사용자를 읽는" 타이밍에서만 나온다.
- **해결**: 라운드마다 로그인 시작을 0~132ms 늦춰서 그 타이밍을 훑었다. 수정 전 코드에서 2~4번째 라운드(약 24ms 지연)에 "재설정이 성공했는데 세션이 1개 남음"이 재현됐다.
- **교훈**: 동시성 버그는 "같은 순간에 시작"만으로는 안 드러날 수 있다. 재현이 안 되면 수정하지 않는 게 아니라 **타이밍을 바꿔서** 다시 시도한다. 그래도 안 되면 그렇다고 기록한다.

### 3-2. 제가 틀린 추론: Hibernate의 잠금 SQL
- **상황**: 교착 가능성을 따지려고 Hibernate jar 안에서 `for no key update` 문자열을 검색했는데 나오지 않아서 "일반 `FOR UPDATE`를 쓴다"고 판단했고, 그에 따라 `refresh`와의 교착을 예상했다.
- **실제**: 테스트 실행 로그의 SQL에는 `for no key update`가 180건 있었다. 문구가 클래스 상수로 들어 있지 않아 문자열 검색으로는 안 보였을 뿐이다. 교착이 재현되지 않은 이유가 이것이었다.
- **교훈**: 라이브러리 내부 동작은 jar 문자열 검색으로 추정하지 말고 **실제로 실행된 SQL/로그**로 확인한다. (다만 이 확인은 교착만 본 것이어서 `refresh` 잠금이 필요 없다는 결론은 틀렸고, 2-3에서 정정했다.)

### 3-3. 테스트 라운드를 줄인 뒤에도 버그를 잡는지 확인
- 테스트 시간을 줄이려고 라운드를 20에서 12로 줄이고 지연 간격을 키웠다. 줄인 뒤에도 유효한지 보려고 **잠금을 임시로 제거하고 실행**했더니 두 테스트(동시 로그인 세션 3개, 재설정 후 세션 남음)가 모두 실패했고, 잠금을 복구한 뒤 3회 연속 통과를 확인했다.
- **교훈**: 경쟁 테스트를 조정한 뒤에는 "수정 없이 실패하는가"를 다시 확인한다. 안 하면 항상 통과하는 테스트가 될 수 있다.

### 3-4. 기존 테스트의 고정값 검증이 깨졌다
- `Retry-After`를 `"60"`, `"3600"`으로 확인하던 통합 테스트는 실제 시계를 쓰므로 남은 시간이 조금 줄어든 값이 나온다. 범위(1~60, 3500~3600)로 바꾸고, 정확한 값은 시계를 조작하는 `AuthRateLimiterTest`로 옮겼다.

## 4. 검증 결과

- **자동 테스트 128개 통과**(기존 116 + 신규 12): `Retry-After` 6건(재설정 남은 시간, 올림·최소 1초, 1밀리초 미만 잔여분 올림 2건, 연장되지 않음, IP), 로그인·갱신 경쟁 6건(재설정과 로그인, 동시 로그인, 갱신과 로그인, 갱신과 재설정, 오답 로그인은 잠금 비대기, 갱신은 잠금 대기).
- 수정 전 코드로 재현을 먼저 확인했다(동시 로그인 세션 3개, 재설정 뒤 세션 1개 남음). 수정 후 3회 연속 통과했고, 잠금을 임시로 제거하면 다시 실패함을 확인한 뒤 복구했다.
- 경쟁 테스트는 로컬 DB에 실제로 커밋했다가 직접 지운다(잔여 데이터 0건 확인).
- **전체 테스트 시간이 약 1분 늘었다**(경쟁 테스트가 bcrypt와 여러 라운드를 돈다).
