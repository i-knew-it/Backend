## 2. 흐름

```
[비밀번호 찾기 화면] POST /auth/password/forgot {email}   → 항상 200
   └ (이메일 로그인 계정이면) 토큰 생성·해시 저장 → 커밋 후 비동기로 메일 발송
[메일] {FRONTEND_URL}/reset-password?token=...  (30분, 1회용)
[재설정 화면] POST /auth/password/reset {token, newPassword, newPasswordConfirm}
   └ 성공 시 비밀번호 변경 + 그 사용자의 모든 Refresh Token 삭제 → 로그인 화면으로
```

## 3. 결정 사항과 이유

### 3-1. AWS SES 대신 SMTP + 로컬 Mailpit
- **선택**: `spring-boot-starter-mail`(SMTP)로 구현. 로컬은 docker compose의 Mailpit(가짜 메일 서버)이 메일을 받고 `http://localhost:8025`에서 볼 수 있다.
- **이유**: SES는 SMTP 접속도 지원하므로, 나중에 코드 변경 없이 환경변수(`MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM`)와 prod 프로필의 SMTP 인증 옵션만 채우면 된다. AWS 설정을 기다리지 않고 메일 내용·링크·발송 코드까지 실제처럼 검증할 수 있다.
- **대안(로그에 링크만 출력)을 택하지 않은 이유**: 가장 간단하지만 메일 발송 코드를 검증하지 못하고 토큰이 로그에 남는다.
- **Mailpit은 `127.0.0.1`에만 바인딩**해 같은 PC에서만 접근된다.
- **SES를 쓸 때 별도로 필요한 것**: 발신 이메일/도메인 인증, 샌드박스 해제(처음에는 인증된 수신자에게만 발송 가능).

### 3-2. 토큰 설계
- 32바이트(256bit) 랜덤을 URL에 안전한 Base64(43자)로 만든다. 추측이 불가능하다.
- **DB에는 SHA-256 해시만 저장**(`token_hash`). 원문은 메일 링크에만 있다. DB가 유출돼도 링크를 만들 수 없다. (Refresh Token과 같은 원칙)
- **1회용 + 30분**. 사용 여부와 만료 확인을 **한 번의 UPDATE**(`markUsed`)로 처리해 같은 토큰으로 동시에 두 번 재설정하는 경쟁 상태를 막는다.
- **사용자당 유효한 토큰은 1개**: 새로 요청하면 이전 링크는 삭제되어 쓸 수 없다.
- 만료, 이미 사용, 존재하지 않음을 **구분하지 않고** 같은 오류(`INVALID_RESET_TOKEN`, 400)를 준다. 토큰 추측에 단서를 주지 않기 위해서다.

### 3-3. 가입 여부를 알 수 없는 응답
- `forgot`은 이메일이 가입돼 있든 없든 항상 같은 200(본문 없음)이다. 가입 여부를 알아내는 공격(이메일 열거)을 막는다.
- **요청 제한(같은 이메일 1시간 3회)도 가입 여부와 무관하게 센다.** 가입된 이메일에만 제한을 걸면 429 여부로 가입 여부가 드러난다. 가입 안 된 이메일도 4번째에 똑같이 429가 된다(테스트로 확인).
- Google로만 가입한 계정(비밀번호 없음)에는 메일을 보내지 않고 같은 응답을 준다.
- **감수한 비용**: 누군가 남의 이메일로 3번 요청하면 그 사람이 1시간 동안 재설정을 요청할 수 없다. 메일 폭탄 방지와 맞바꾼 것이다. 필요하면 "이메일+IP" 조합 제한을 병행하는 방안을 검토한다.
- **한계**: 메일 발송은 비동기라 응답 시간에 드러나지 않지만, 가입된 이메일일 때만 DB 쓰기(토큰 삭제·저장)가 있어 아주 미세한 응답 시간 차이는 남는다. 완전히 제거하지는 못했다.

### 3-4. 재설정에 성공하면 모든 기기를 로그아웃
- 그 사용자의 Refresh Token을 모두 삭제한다. 계정이 탈취된 상황에서 비밀번호를 바꿨는데 공격자의 세션이 살아 있으면 의미가 없다. 단일 디바이스 정책과도 맞는다.
- **한계**: Access Token은 DB를 확인하지 않아 최대 30분은 유효하다.
- 성공 후 자동 로그인은 하지 않는다. 새 비밀번호로 직접 로그인하게 한다.

### 3-5. 검증 순서: 비밀번호 검증을 먼저, 토큰 소모는 나중에
- 비밀번호 규칙·확인 불일치를 토큰 확인보다 먼저 검사한다. 규칙에 맞지 않는 비밀번호로 시도해도 링크가 소모되지 않아 다시 시도할 수 있다(테스트로 확인). 사용자가 오타 한 번에 링크를 날리지 않게 하기 위해서다.

### 3-6. 메일은 커밋 후 비동기 발송 (이벤트 + AFTER_COMMIT + @Async)
- **커밋 후**: 토큰 저장이 롤백됐는데 링크가 메일로 나가는 문제를 막는다.
- **비동기**: 메일 서버 지연이 응답 시간에 드러나지 않고, 메일 실패가 요청 실패로 이어지지 않는다(응답이 가입 여부에 따라 달라지지 않게 하기 위해서이기도 함).
- 발송 실패는 예외 종류만 로그에 남기고 **이메일 주소와 토큰은 남기지 않는다**. 이벤트(`PasswordResetRequested`)의 `toString`도 값을 가린다.
- 메일 서버 타임아웃을 5초로 제한해 발송 스레드가 오래 매달리지 않게 했다.

### 3-7. 비밀번호 정책 공통화 (`PasswordPolicy`)
- 가입과 재설정이 같은 규칙(정규식, 메시지, 확인 일치, 72바이트 제한)을 쓰도록 한곳으로 모았다. 한쪽만 고쳐서 규칙이 어긋나는 일을 막는다. 기존 가입 동작과 테스트는 그대로다.

### 3-8. 그 외
- **링크 경로** `/reset-password?token=...`은 설정(`app.password-reset-path`)이라 프론트가 다른 경로를 쓰면 값만 바꾸면 된다. 프론트가 이 경로의 페이지를 구현해야 한다.
- **발신 주소** `MAIL_FROM`(기본 `no-reply@anunjul.app`)은 SES에서는 인증된 주소여야 한다.
- 만료된 재설정 토큰은 기존 Refresh Token 정리 스케줄러(매일 03:00 KST)에서 함께 삭제한다.
- CodeRabbit 엔티티 목록에 `PasswordResetToken`을 추가했다(새 엔티티를 만들면 목록도 갱신해야 한다는 일지 항목을 실행).

### 3-9. 같은 사용자의 동시 요청은 사용자 행 잠금으로 순서화 (CodeRabbit 리뷰 반영)
- **문제**: `issueToken`은 "기존 토큰 삭제 → 새 토큰 저장"인데, 같은 사용자의 요청이 동시에 오면 둘 다 삭제(0건)를 거친 뒤 둘 다 저장해 **유효한 토큰이 여러 개** 남는다. "새로 요청하면 이전 링크는 무효"라는 약속이 깨진다. 수정 전에 테스트로 먼저 재현했고, 3개 스레드가 동시에 요청하자 첫 라운드부터 토큰이 3개 남았다.
- **선택**: `SELECT ... FOR UPDATE`로 **사용자 행을 잠그고** 조회해서 같은 사용자의 발급을 한 번에 하나씩 처리한다(`findByEmailForUpdate`). 스키마 변경은 없다.
- **`UNIQUE(user_id)`를 택하지 않은 이유**: 두 번째 요청이 중복 키 오류로 실패하는데, 이 오류는 **가입된 이메일에서만** 생겨 응답으로 가입 여부가 드러난다(우리가 막으려던 것). 재시도 동작도 따로 설계해야 한다. 또 적용된 `V4` 마이그레이션을 수정하면 Flyway 체크섬 불일치로 기동이 실패한다.
- **재설정도 같은 순서로 잠가야 한다(교착 방지)**: 요청 쪽만 잠그면 요청은 "사용자 행 → 토큰 행", 재설정은 "토큰 행 → 사용자 행" 순서가 되어 서로를 기다린다. 실제로 두 번째 테스트에서 `deadlock detected`가 발생했다. 그래서 `resetPassword`도 사용자 행을 먼저 잠그도록 순서를 바꿨다(`findByIdForUpdate` → 토큰 사용 처리 → 사용자 재조회).
- **재조회가 필요한 이유**: `markUsed`가 `clearAutomatically`로 영속성 컨텍스트를 비우기 때문에, 그 앞에서 잠그며 읽은 사용자 객체는 분리(detached)되어 비밀번호 변경이 저장되지 않는다. 이미 잠근 행이라 다시 읽어도 기다리지 않는다.
- **같은 토큰 동시 재설정**은 원래 `markUsed`(조건부 UPDATE 한 번)가 막고 있어서 코드 수정은 필요 없었고, 이를 확인하는 테스트만 추가했다.

## 4. 겪은 문제와 해결 (트러블슈팅 소재)

### 4-1. 테스트에서 메일 리스너가 실행되지 않음 → 이벤트로 토큰 확인
- **상황**: 통합 테스트는 `@Transactional`이라 트랜잭션이 커밋되지 않는다. 메일 리스너는 `AFTER_COMMIT`이라 **실행되지 않고**, 따라서 실제 메일도 나가지 않는다. 의도한 동작이지만 토큰 원문을 테스트에서 어떻게 얻느냐가 문제였다.
- **해결**: `@RecordApplicationEvents`로 발행된 `PasswordResetRequested` 이벤트를 꺼내 토큰을 확인한다. 메일 내용(링크, 수신자, 발송 실패 시 예외 미전파)은 리스너 단위 테스트(Mockito)로 따로 검증하고, 실제 SMTP 구간은 Mailpit으로 직접 확인했다.

### 4-2. IDE의 오탐 진단 두 가지
- `docker-compose.yml`에 "Map keys must be unique (mailpit)" 오류가 떴지만 파일에는 `mailpit` 키가 1개였고 YAML 파싱도 성공했다(저장 도중의 일시적 상태).
- `PasswordPolicy cannot be resolved`는 파일을 만든 직후 IDE 인덱스가 지연된 것으로, 실제 컴파일은 통과했다.
- **교훈**: IDE 진단과 실제 빌드 결과가 다르면 빌드/파서 결과를 기준으로 판단한다.

### 4-3. 재설정이 Refresh Token을 지우는지 확인하는 테스트가 아무것도 검증하지 못하고 있었음
- **발견**: CodeRabbit이 `재설정하면_새_비밀번호로만_로그인되고_모든_기기가_로그아웃된다` 테스트의 검증 순서를 지적했다. 이 테스트는 재설정 직후 **새 비밀번호로 로그인**한 뒤에 기존 Refresh Token으로 갱신이 실패하는지 확인했다.
- **원인**: 로그인하면 단일 디바이스 정책(`startSession`)으로 기존 Refresh Token이 **어차피 모두 삭제**된다. 그래서 그 뒤의 갱신 실패는 재설정 때문이 아니라 방금 한 로그인 때문이다. **재설정이 토큰을 지우지 않게 되어도 이 테스트는 통과**한다. 회귀를 잡지 못하는 테스트였다.
- **수정**: 재설정 직후 로그인보다 먼저 `refresh_tokens` 행이 0개인지, 기존 토큰 갱신이 `TOKEN_INVALID`로 실패하는지 확인한다. 재설정 전에는 행이 1개인 것도 확인해서 "지워졌다"는 것이 의미 있게 한다.
- **교훈**: 한 정책(단일 디바이스)이 다른 동작의 검증을 가려 버릴 수 있다. 부수 효과가 있는 동작을 검증할 때는 그 동작 직후, 다른 호출을 하기 전에 상태를 확인한다.

### 4-4. 경쟁 상태는 "고친 뒤 통과"만으로는 부족하고 먼저 재현해야 한다
- 동시성 테스트는 운이 좋으면 통과할 수 있어서, **수정 전 코드로 먼저 실행해 실패하는 것을 확인**한 뒤 수정했다(3개 스레드 × 8라운드, 시작 신호를 맞추는 `CountDownLatch` 사용). 수정 후에는 세 번 연속 통과시켜 안정성을 확인했다.
- 단계적으로 고치며 새 문제(교착)도 같은 테스트로 발견했다. 한 곳만 고치면 다른 곳과 충돌할 수 있어서, 잠금처럼 순서가 중요한 변경은 관련된 모든 경로를 함께 검토한다.
- 이 테스트는 서로 다른 트랜잭션이 필요해 `@Transactional`을 쓸 수 없고 데이터가 실제로 커밋되므로, 만든 사용자와 토큰을 직접 지우고, 커밋되면 실행되는 메일 리스너는 `JavaMailSender`를 목으로 대체해 실제 발송을 막았다.

## 5. 검증 결과

- **자동 테스트 116개 통과**(기존 88 + 신규 28): 재설정 요청(해시만 저장, 만료 30분, 이벤트 발행, 가입 여부 무관 동일 응답, 소셜 전용 계정, 이메일 대소문자, 이전 링크 무효화, 요청 제한과 429), 재설정(세션 전체 삭제, 1회용, 만료, 잘못된 토큰, 규칙 위반 시 링크 유지, 72바이트, 탈퇴 계정), 메일 내용·실패 처리·로그 노출, 이메일당 제한기(시간 제어), 정리 스케줄러, 동시성(같은 토큰 동시 재설정에서 정확히 하나만 성공, 같은 사용자의 동시 요청에서 토큰 1개만 유지, 재설정과 요청이 동시에 와도 교착 없음).
- **실제 서버 + Mailpit**: 가입 → 재설정 요청(가입된 이메일과 없는 이메일 모두 200, 본문 길이 0) → Mailpit에 가입된 이메일 1통만 도착 → 링크 형태 `http://localhost:3000/reset-password?token=...` 확인 → 약한 비밀번호 400 → 올바른 비밀번호 200 → 새 비밀번호 로그인 200, 옛 비밀번호 401 → 같은 링크 재사용 400. 검증용 계정과 메일은 삭제함.
